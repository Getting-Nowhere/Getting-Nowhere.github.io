Most Active Directory compromises do not depend on one flaw. They depend on weak defaults that stack: shared local administrator passwords, broad rights to edit Group Policy, service accounts with long-lived passwords, and little audit logging. This page lists the baseline controls that break those chains. Use it to check each control during an assessment, and as a starting point when recommending fixes.

## Baseline controls

| Control | What it does | Attack path it limits |
|---|---|---|
| LAPS | Randomises and rotates the local administrator password on each Windows host | Password reuse across hosts and pass-the-hash to many machines |
| Advanced audit policy | Records logons, account changes, directory changes, privilege use, and policy changes | Detection of password spraying, ACL changes, and replication abuse |
| GPO security settings | Sets account, local, software restriction, application control, and audit policy | Excess user rights and unsafe local configuration |
| WSUS or SCCM | Centralises patch deployment | Exposure to publicly known flaws in domain services |
| Group Managed Service Accounts (gMSA) | Gives a service a domain-managed password, generated by the DC (about 120 characters) and rotated automatically | Kerberoasting of human-managed service accounts |
| Small privileged groups | Keeps membership of Domain Admins, Backup Operators, and similar groups to the minimum | Privileged group abuse and nested membership surprises |

## Hardening steps

1. Deploy LAPS to every domain-joined workstation and server. Restrict which groups can read the LAPS password attribute.
2. Enable the advanced audit policy for logon, account management, directory service changes, and Kerberos service ticket operations.
3. Move service accounts to gMSA wherever the application supports it.
4. Keep WSUS or SCCM patching current, prioritising the flaws listed in the bleeding-edge page.
5. Review the built-in privileged groups and remove members who do not need them.
6. Review every GPO's security settings, and who is allowed to edit each GPO.

## Group Policy security settings

Settings fall into five groups:

- **Account policies**: password and account lockout policy.
- **Local policies**: audit policy, user rights assignment, and whether users can install drivers.
- **Software restriction policies**: which software can run on a host.
- **Application control policies**: which applications specific users or groups may run.
- **Advanced audit policy configuration**: file access, logon and logoff, policy changes, and privilege use.

## Validation commands

```powershell
Get-ADGroupMember -Identity "Domain Admins"
Get-ADGroupMember -Identity "Backup Operators"
Get-ADUser -Filter {ServicePrincipalName -ne "$null"} -Properties ServicePrincipalName
Get-ADGroup -Identity "Server Operators" -Properties Members
```

## What to look for

- A local administrator password that works on more than one host. A single authentication attempt per host confirms reuse.
- Service accounts with SPNs and passwords that have not changed in years.
- Audit gaps. If logon auditing is off, password spraying leaves no evidence to find.
- Privileged groups with more members than the business case allows, including members added through nested groups.

> A control that exists on paper can still do nothing. Confirm that each GPO is linked to the OU that holds the target objects, and that LAPS is installed on the hosts you can reach.
{: .tip }

## Pitfalls

- LAPS rolled out to servers only leaves workstations reusing a shared password.
- gMSA accounts suit non-interactive services. Do not assume they fix a human account with a weak password.
- Hardening GPO content while leaving GPO edit rights open is a half measure. See [Group Policy](/methodology/active-directory/group-policy/).
